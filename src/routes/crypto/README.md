# 加解密工具箱 · /crypto

> 在线使用：<https://www.toolv.cn/crypto> ・ 密钥与内容全程只在浏览器内存里，不上传、不落库

一页五个工作区（标签切换），对应待开发清单里的 ID 45–49 —— 都是「小而专」的加解密小工具，
按仓库「功能相近合并成一页」的约定收在同一个入口下。

五个工作区的输入 / 结果卡片标题行各有一枚**全屏**按钮（原生全屏 API，Esc 退出），长密文与长结果可单独铺满屏幕看。

## 已实现的能力

### AES（ID 45）

- **三种模式**：CBC / GCM / CTR，各自的 IV（计数器）长度按 WebCrypto 的硬要求校验，长度不对时直接说清楚该填多少
- **三档密钥**：16 / 24 / 32 字节 → AES-128 / 192 / 256，按实际字节数判定档位
- **密钥与 IV 各有两种 / 三种输入格式**：密钥可写文本 / Hex / Base64，IV 可写 Hex / Base64
- **随机生成**：按档位生成随机密钥（16 / 24 / 32 字节）、按当前模式生成长度正确的随机 IV
- **输出 Hex / Base64 任选**：这个格式同时是解密时的输入格式，一个开关两个方向都管
- **失败给人话**：密钥长度不对、IV 长度不对、CBC 密文不是 16 的倍数、GCM 认证标签不通过，都有一句中文说明
- **结果不会偷偷过时**：改过任何参与运算的参数后，状态条会变成琥珀色提醒「重新点一次」

### RSA（ID 46）

- **生成密钥对**：2048 / 3072 / 4096 位，导出 PKCS#8 私钥（`BEGIN PRIVATE KEY`）与 SPKI 公钥（`BEGIN PUBLIC KEY`），与 openssl 通用
- **加解密**：RSA-OAEP + SHA-256；明文超过单次上限（密钥字节数 − 66）时点名上限是多少，不吐 DOMException
- **签名验签**：RSASSA-PKCS1-v1_5 + SHA-256（与 JWT 的 RS256 同一套），签名输出 Base64
- **四档操作**共用一把密钥对：同一次生成的材料，加解密与签名验签都能用（WebCrypto 把算法绑在密钥上，这里按用途重新导入同一份 DER）
- **导入既有密钥**：直接粘 PEM 即可；PKCS#1 的两种老写法不现场解，给一句 openssl 转换命令
- **「本次使用」徽章**：标出当前操作需要的是私钥还是公钥，不用自己推

### HMAC（ID 47）

- **四种摘要**：SHA-1 / SHA-256 / SHA-384 / SHA-512，摘要字节数在状态条上报出
- **密钥三格式**：文本 / Hex / Base64；只敲空格等于没填，会明确报「密钥是空的」
- **输出 Hex / Base64**，可一键随机生成 32 字节密钥
- **实时重算**：密钥、消息、算法、格式任一变化就重算（异步有竞态序号兜底，晚回来的旧结果作废）

### 凯撒密码（ID 48）

- **位移 0–25**：位移输入接受 29 / −3 这类写法，自动收敛到 0–25；一键 ROT13
- **位移对照表**：26 个字母的映射一行排开、横向滚动，方向跟着「加密 / 解密」翻过来
- **只动拉丁字母**：数字、标点、中文原样保留，大小写跟着原字母

### 维吉尼亚密码（ID 49）

- **自定义密钥**：密钥只取字母（其余字符忽略），按字母位置循环复用
- **密钥预览**：把密钥按字母位置铺开、与原文逐位对齐（非字母位置保留原字符），一眼看出密钥怎么重复
- **非字母不消耗密钥位**：`A-A` 用密钥 `BC` 得到 `B-C`

### 通用

- **整页预渲染**：标签条与五个工作区的空态都在 HTML 里，首屏可读，利于 SEO
- **复制**：每个工作区的结果、RSA 的私钥与公钥都有独立复制按钮
- **示例**：五个工作区各有一份示例（AES 的示例是一组 AES-256 / CBC 的经典取值）

## 参数在哪调

业务参数在根目录的 `config.ts`：默认落在哪个工作区、五个工作区的示例数据、
AES 的模式 / 格式 / 随机密钥档位清单、RSA 的模数清单、HMAC 的算法清单、凯撒位移范围与维吉尼亚密钥上限。

**没有放进去的两类**：算法的硬约束（AES 各模式的 IV 长度在 `core/aes.ts` 的 `IV_LENGTH`，
那是 WebCrypto 的要求而不是可调参数）、组件里的提示文案（在各 `ui/*.svelte`）。

## 档位

**L2**（`+page.svelte` + `core/store.svelte.ts` + `ui/*.svelte`）：五个工作区各有一块面板，
标签切换外壳走共享 `TabShell`（与 `/cheatsheet`、`/morse` 同构）。

`ui/styles.ts` 里只有三串样式（参数条外壳 / 参数条格子 / 结果文本），各自都有两个调用方
（凯撒与维吉尼亚共用参数条、HMAC 与 RSA 共用结果文本），够 `STRUCTURE §0` 的抽出门槛。

## 实现口径

- **一个根 store + 五个子状态类**：`core/store.svelte.ts` 里每个工作区是一个独立的类，
  类的 `$state` 字段本身就是响应式边界 —— 不把三十多个字段摊平在同一个类里靠命名前缀区分归属
- **谁按按钮、谁实时算**（三条不同的交互口径，各有理由）：
  AES / RSA **点按钮执行** —— 方向、模式、格式要先定下来，边打边算会一路报「密文不完整」；
  HMAC **实时重算** —— 只有密钥与算法两个旋钮，跟哈希工具一样即打即出；
  凯撒 / 维吉尼亚用 `$derived` 直接派生 —— 纯函数、没有可失败的地方
- **结果的「过时」用参数指纹判**：AES / RSA 把产出结果时的参数拼成一行存起来（`runKey`），
  与当前参数不一致就把状态条改成琥珀色提醒重算 —— 与 `/jwt-decoder` 的 stale 是同一套思路
- **古典密码不动密钥位**：非字母位置既不参与位移、也不推进维吉尼亚的密钥下标，
  否则「密钥与第几个字母对齐」就不可预期了
- **CBC 的方向反了不会解出乱码**：CBC 的填充校验能挡住大部分错配；GCM 有认证标签；
  只有 CTR 是流式的，解错了会得到随机字节 —— 这时状态条会说明「解密结果不是合法 UTF-8」
- **RSA 的一把钥匙两用**：`generateKey` 只能绑一个算法，所以按 RSA-OAEP 生成并导出 DER，
  签名时把同一份 DER 按 RSASSA-PKCS1-v1_5 重新 `importKey` 一次（见 `core/rsa.ts` 顶部注释）

## 踩过的坑

- **WebCrypto 的入参会卡在 `Uint8Array<ArrayBufferLike>`**（TS 5.7 起 `Uint8Array` 带缓冲类型参数）：
  `crypto.subtle.*` 收的是 `BufferSource`，而 `new TextEncoder().encode()` / `Uint8Array.from()` 之外的函数
  只要**声明返回 `Uint8Array`** 就被拓宽成 `Uint8Array<ArrayBufferLike>`，于是 `subtle.encrypt / sign / verify`
  一律报「not assignable to BufferSource」。口径：字节产出函数显式标注 `Uint8Array<ArrayBuffer>`
  （本工具收成 `core/types.ts` 的 `Bytes` 别名），别在每个调用点包一层 `Uint8Array.from`。

## 已知取舍 / 暂不支持

- **GCM 的 IV 只收 12 字节**：非 96 位的 IV 要先走一遍 GHASH，各语言实现默认行为不一致，
  与其让人以为「多少位都行」，不如拦下来（错误文案里写明了要求）
- **CTR 用整块 128 位计数器**（`length: 128`）：与 openssl 的 `aes-ctr` 一致；这不是可调参数，写死在 `core/aes.ts`
- **GCM 不收附加数据（AAD）**：需要 AAD 的场景用 openssl 或代码里的 WebCrypto，这里不做半套
- **RSA 只收 PKCS#8 私钥与 SPKI 公钥**：PKCS#1 的 `RSA PRIVATE KEY` / `RSA PUBLIC KEY` 会给出 openssl 转换命令，
  不在这里现场包 DER
- **RSA 签名固定 PKCS#1 v1.5（不是 PSS）**：与 JWT 的 RS256 同一套口径；要 PSS 请用 openssl
- **RSA 不做分段加密**：明文超过上限直接报错并给出上限，长内容请用 AES —— 分段 RSA 的填充与拼接口径各家不同
- **不做密钥的本地保存**：密钥只在内存里，刷新即失；要留存请自己复制 PEM 或存进密码管理器
- **古典密码不做自动破译**：凯撒不给「26 种位移全列出来」的暴力破解视图，维吉尼亚不做卡西斯基测试
- **不做文件加解密**：五个工作区都只处理文本框里的内容

## 验证过什么

- 纯逻辑单测 77 条在 `core/*.test.ts`（vitest 的 server project，node 自带 WebCrypto）：
  - `encoding.test.ts`：hex / Base64 / UTF-8 互转、base64url 与缺省填充、非法输入的报错、100KB 内容分块不溢出
  - `aes.test.ts`：三种模式往返、填充与标签的长度特征、参数校验与失败文案；**另有与 `node:crypto` 的互通用例**
    （我们加的密 node 解得开、node 加的密我们解得开），证明产物在 openssl 一侧可用
  - `rsa.test.ts`：密钥生成与 PEM 标签、`derToPem`/`pemToDer` 往返、PKCS#1 的转换提示、
    加解密往返、明文上限的边界（190 可、191 不可）、签名长度等于模数长度、改动原文后验签结论是「无效」而不是报错
  - `hmac.test.ts`：RFC 4231 / RFC 2202 的标准向量（SHA-1 / 256 / 512）、四种算法的长度、
    空消息与空密钥的报错
  - `classical.test.ts`：凯撒 shift 3 的经典例与位移收敛、对照表两个方向、
    维吉尼亚的经典例（LEMON × ATTACKATDAWN = LXFOPVEFRNHR）、非字母不消耗密钥位、密钥预览对齐
  - `store.test.ts`：编排层的状态流转 —— 结果的「过时」判定与恢复、失败时清掉旧结果、
    `loadExample` 摆好的参数、随机密钥 / IV 顺手切到 Hex、RSA 重新生成密钥对后清掉旧结果、
    验签结论映射到状态条语义色、HMAC 实时的空值分支、古典密码的派生结果与错误文案
- 页面侧：SSR 产出的 HTML 里五个标签与空态文案都在（`curl /crypto` 核对），首页卡片与工具菜单由 `src/lib/tools.ts` 数据驱动
- 浏览器实测（Playwright + axe-core，375 与 1280 两个宽度）：五个工作区都无横向溢出、`wcag2a` / `wcag2aa`
  0 violations、控制台 0 报错；并走通主流程 —— AES 示例加密出 48 字节密文、HMAC 出 64 位十六进制、
  凯撒出 `Khoor, Zruog!`、维吉尼亚出 `LXFOPV EF RNHR`、RSA 生成密钥对后加密得 344 字符 Base64 且验签结论为「签名有效」
