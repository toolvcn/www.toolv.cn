# 工具 README 规范（TOOL-README.md）

> 本文件是 `src/routes/<tool>/README.md` 的**写作规范**。
> **写 README 时读 §0-§2 就够**（骨架 / 固定区块 / 其余节）；§3 是硬规则，动手前扫一遍。引用写作 `TOOL-README §2`。
>
> 分工：**流程、runes、测试、门禁看 `AGENTS.md`；目录与档位看 `STRUCTURE.md`；样式取值看 `UI-STYLE.md`；提交看 `COMMIT.md`；本文件只管工具 README 怎么写。**

**一句话**：工具 README 是**这个工具已实现能力的清单 + 读代码看不出来的口径**。

## 0. 骨架（照这个抄）

```md
# <工具名> · /<路由>

> 在线使用：<https://www.toolv.cn/<路由>> ・ 数据全部本地处理，不上传、不落库

<可选：一到两句导语>

- **<能力名>**：<是什么 + 边界>

## 参数在哪调

## 档位

## 实现口径

## 踩过的坑

## 已知取舍 / 暂不支持

## 验证过什么
```

- 前三个区块**固定**（标题行 / 承诺行 / 能力清单，写法见 §1）；**导语段可选** —— 一到两句，说清这页是干什么的、
  有哪几个工作区，**只在标题不够用时写**：clock 的「三合一」、cheatsheet 的「九张表一页切换」值得写，
  `# 单位换算 · /unit-converter` 后面再来一句「用于单位换算」就是废话。
- 模板里那 6 个 `##` 只是**最常用的候选**：通用节的完整清单见 §2.1 / §2.2，**这一页独有的节可以自取节名**（§2.4），
  逐条判断要不要写；**用不到的整节删掉，不要留空节**。

## 1. 固定区块怎么写

### 1.1 标题行

`# <工具名> · /<路由>`。工具名取首页工具列表与工具页里的**正式名**，可以和路由名不同（`# 加解密工具箱 · /crypto`）；
分隔是 `·`（空格 + 间隔号 + 空格）；有两个常用叫法时允许再接一段（`# 悬浮时钟 · 计时器 · /clock`）。
**不要出现「README」二字。**

### 1.2 承诺行

骨架的第 2 行。**前半句固定**（`在线使用：` + `https://www.toolv.cn/<路由>` + `・`），
**后半句按这个工具真实的数据流写** —— 它是本站对外承诺的一部分（与首页「数据本地处理」同源），
**只准比默认更严，不准放宽**：

| 这个工具的真实情况               | 后半句怎么写 | 现例                                                        |
| -------------------------------- | ------------ | ----------------------------------------------------------- |
| 数据不出浏览器（绝大多数）       | 用默认句     | `数据全部本地处理，不上传、不落库`                          |
| 只读本机信息，没有「数据」可谈   | 换动词       | device-info：`数据全部本地读取，不上传、不落库`             |
| 页面根本不发请求                 | 说清不联网   | dns：`静态清单与命令模板，全程不联网、不上传`               |
| 处理密钥 / 口令这类敏感材料      | 补数据边界   | crypto：`密钥与内容全程只在浏览器内存里，不上传、不落库`    |
| 容易被误会会连外部系统           | 追加否定     | sql：`数据全部本地处理，不上传、不落库、不连数据库`         |
| 有服务端路径（**全站唯一例外**） | 必须自己写明 | http：`默认浏览器直发、数据本地处理；可开启「服务器代发」…` |

判据是「读者会不会误判数据去了哪」：会就按上表改，不会就用默认句。

### 1.3 能力清单的整体形态

**默认不加标题**，直接接在导语 / 承诺行后面 —— README 的主体就是这份清单，再给它安一个
`## 已实现的能力` 等于给正文加目录。只有清单本身要分组时才用它当容器，组内用 `### <组名>`
（crypto 的「五种算法 + 通用」、htaccess-to-nginx 是这个形态），
按**用户会怎么用**分（按算法、按工作区），不要按代码模块分。

### 1.4 能力清单里一条怎么写

```md
- **<能力名，6-12 字>**：<是什么。><边界 / 口径 / 例外。>
```

- **能力名加粗**，是扫读时的索引 —— 十来条读完就知道这页有什么、能不能解决自己的问题。
- **「是什么」要具体到能被验证**：「九类命令按组列出，共 65 条」比「支持命令速查」有用得多；写实际值，不写「若干」「多种」。
- **「边界」是最容易漏、也最值钱的那半句**：上限（2 MB / 10000 条 / 50 条片段 / 20 万字符）、
  口径（6 位有效数字 / 月按 30 天折算 / `+` 按字面、空格按 `%20`）、
  例外（只标注不弹窗确认 / 筛选只影响渲染 / 认不出来的地址参数当作没写）、
  降级（超长内容整段按纯文本渲染 / 坏字节原样保留、不拖垮整批）。
- **一条一句到三句**。「算法 / 模型 / 公式」这类要展开的，说明它是**口径**而不是能力，挪到 §2 的 `## 实现口径` 或 `## 数据口径`。
- **形式**：清单不用表格（表格留给「一组同类项横向对照」，如 cheatsheet 的七张表）；次级要点用嵌套 `-`；
  代码、参数名、路径挂反引号。

**别只写主流程** —— 下面这些「顺手做掉的小能力」最容易在 README 里失踪，而它们往往正是
「为什么用这一页而不是别处」的答案，逐条自查：

- **预设**：存哪 / 键名 / 上限 / 怎么删 / 能否导入导出 JSON
- **导出**：文件名 / 导的是全部还是当前筛选结果
- **复制**：逐行复制 / 一键复制全部 / 复制的是原串还是渲染结果
- **配置写进地址**：哪些参数 / 没写的项怎么回落 / 同时开多份会怎样
- **交互形态**：全屏放大 / 拖动排序 / 快捷键
- **搜索筛选口径**：匹配哪些字段 / 多词 AND 还是 OR / 空词与无结果各什么行为
- **危险操作怎么处理**：只标注？二次确认？为什么这样选
- **空态与错误文案**：「还没输入」与「筛不出结果」给了不同文案吗
- **SSR 首屏里能读到什么**：整张表 / 空态骨架 / 默认那条结果

## 2. 其余节（按需）

骨架之外的节分两类：**常规六节**（§2.1，节名照抄，不要另起同义名）与**专属节**
（§2.2 里已收编的照抄节名；§2.3 / §2.4 里这一页独有的自取节名）。
两类都按「何时写」判断，不满足就整节省略 —— **空节比没有更糟**；
**节名里都不要放数目**（条数一变标题就对不上）。

**位置**：专属节插在**能力清单之后**；常规六节彼此保持 §0 骨架里的相对顺序
（`参数在哪调` → `档位` → `实现口径` → `踩过的坑` → `已知取舍 / 暂不支持` → `验证过什么`），
但**不要求这六节连成一块** —— 与某一节同源的专属节就紧挨着它放（`刻意不统一` / `数据口径`
常见的位置是跟在 `实现口径` / `踩过的坑` 之后、`已知取舍` 之前）。读的人先看「这一页是什么、怎么用」，
再看维护口径；专属节之间也按这个顺序串（怎么用 → 为什么这么定 → 边界）。

### 2.1 常规六节

| 节名                     | 什么时候写                                                                      | 写什么                                                                                                                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `## 参数在哪调`          | 只要工具有可调的业务参数（默认值 / 档位 / 上限 / 存储键）                       | 参数在哪。**有 `config.ts` 就点名它在 `config.ts`**（顺手写关键键名）；**没有就明说「没有 `config.ts`」**，写清参数落在 `core/xxx.ts` 的哪几个常量、为什么没到建它的门槛。目标是「改一个数该动哪个文件」一眼可见  |
| `## 档位`                | 建了 `core/store.svelte.ts` 的工具（L1 / L2）                                   | 落在 L0 / L1 / L2 哪一档、为什么；`core/` 与 `ui/` 各放了什么；建没建 `ui/styles.ts`。L2 写清拆了哪几个面板；界面或逻辑在共享层时（docker / git / linux / sql）写清**哪些不在本目录**，免得下一个人在本目录里空找 |
| `## 实现口径`            | 有非显然的实现决策：算法与精度、竞态与节流、安全边界、为什么不用某个 API 或依赖 | 只写**读代码看不出来的**：为什么不 `eval`、为什么自写 MD5、浮点噪声在哪一层收拾、计时为什么不累加、计时进度为什么不落盘。不要复述函数在做什么                                                                     |
| `## 踩过的坑`            | 这个工具曾踩过、且容易再踩的坑                                                  | 只写**本工具特有**的：怎么坏的 + 现在怎么防 / 别再这么写。跨工具 / 环境 / 操作层面的坑不写这里（→ `docs/MEMORY.md`）；一次性笔误、已修好且不会复发的普通 bug 不写                                                 |
| `## 已知取舍 / 暂不支持` | 几乎每个工具都该有                                                              | 这页**刻意不做**的事 + 为什么，按「免得被当成 bug」写：不做变量与赋值、不做货币汇率（要联网）、不做音频播放、不做语法校验                                                                                         |
| `## 验证过什么`          | 有单测或做过浏览器实测                                                          | 测了什么（文件路径 + 条数 + 断言重点）、浏览器实测过什么（375 / 1280 无横向溢出、axe 0 violations）。**不要**把断言逐条抄进来，那属于测试文件                                                                     |

### 2.2 工具族专属节（用到了才写）

| 节名                          | 什么工具用                                                                  | 写什么                                                                                                                                                  |
| ----------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `## 刻意不统一`               | 做法与别处不同、读者会以为是 bug                                            | 逐条写「这里和哪不一样 + 为什么不一样」。现例：docker / git / linux / sql 的危险命令只标注不弹确认、clock 的 `ClockStage.svelte` 一处 Tailwind 类都不用 |
| `## 数据口径`                 | 内容型工具（dns / git / linux / sql / cheatsheet）                          | 收录范围与取舍：只收通用子命令、`note` 记的是坑与代价、`+1` 是 NANP 主区、分裂时期按并立政权各列一行                                                    |
| `## 它解决什么`               | 口径复杂、得先对齐「算的是什么」的计算类工具                                | ecommerce-roi 的两种口径（整盘 / 单件）、退货分三类怎么分别记账                                                                                         |
| `## 界面布局`                 | 版式本身就是重点、或结构极易改错的多面板工具                                | 只写「改之前必须先知道」的结构约束（哪一栏滚、封顶多少）；**纯版式取值不写**，那是 `UI-STYLE` 的事                                                      |
| `## 目录结构` + `## 分层约定` | **特例，慎用**：结构跨到共享层、且它本身就是这页的维护重点（目前只有 http） | 只画与本工具相关的那部分和分工。绝大多数工具**不要**写这节                                                                                              |

### 2.3 能力清单的分组节

能力清单内部有「两个工作区 / 两张表 / 一个独立窗口」这种形态时，允许按工具自取节名
（cheatsheet 的「两张专属形态的表」「七张通用速查表」、clock 的「独立窗口 `/clock/display`」、
http 的「请求调试」「查看响应」）。位置固定在**能力清单之后、口径类节之前**；节名要能自解释，别只写「说明」「其它」。

### 2.4 工具专属节（自己取节名）

§2.1 / §2.2 那两张表**只收录已经重复出现的节**，不可能预先穷举。这一页有别的页没有的东西
（多工作区 / 独立窗口 / 一张对照表 / 一套业务模型 / 一段得先对齐的口径）时，
**允许自取 `## <节名>`**，插在**能力清单之后、通用节之前**。写法：

- **判据是「装不进通用节」**：塞进 `## 实现口径` 会变成一节里讲三件事，或读者不先看代码就看不懂这段在讲什么。
  能装下的照抄通用节名，别另起一个 —— 同一件事两种叫法，下一个人会两边找。
- **节名自解释**：一看就知道这段讲什么。`## 说明`、`## 其它`、`## 补充`、`## 注意事项` 一律不合格 ——
  它们只是「不知道放哪」的垃圾桶；属于哪类就照抄哪类通用节名。
- **一节一个主题**：两件事挤进一个节等于没有节；名字里能并列的（`A 与 B`）只在两项确实同源时才写。
- **宜少不宜多**：专属节多到需要目录，说明这一页该拆（页内标签切换）或该把内容压回能力清单。
  小工具只写骨架 + 通用节，**不因为「别的页写了」补一个**。
- **不借机扩写通用内容**：专属节同样受 §3 管 —— 不复述目录与逐文件内容、不复述通用规范、不写待办与路线图。
- **反复出现就上提**：同一个节名在两三个工具里都长出来了，就把它收进 §2.2 那张表（**那张表是唯一维护处**），
  各工具改回照抄。专属节是这套规范的入口，不是各页自由发挥的出口 —— 放任它就会长出十个近义节名。

## 3. 硬规则

1. **每个工具目录必须有 `README.md`，随目录一起建**（`STRUCTURE §1`），首页的 📄 指向它；
   加完能力要把新能力（含边界）补进清单（流程见 `AGENTS.md` §9 第 3 条）。
2. **不复述目录结构与逐文件内容**。`ls` 一眼能看到的东西写进来只会随重构过期；要写的是「为什么这么分」（进 `## 档位`）。
   同理，**别把内部设计抄成文档** —— 一屏函数名与数据流，读者看完还是不知道该不该用这页。
3. **只写现状**：不写待办 / 路线图 / 「后续计划」。「暂不支持」说的是「这页刻意不做」，
   不是「以后有空做」—— 两者混在一起，下一个人就会把刻意不做的事当待办捡起来重做。
4. **不出现工具 ID**（指认工具用名称或路径）；**不插截图** —— 承诺 + 能力清单就够了。
5. **不复述通用规范**。runes 约定、档位阈值、颜色与间距取值、门禁清单各有唯一定义处
   （见 `AGENTS.md` 顶部那张规范清单），README 只记「这一页特有」的。
6. **链接用绝对地址**：承诺行写 `https://www.toolv.cn/<路由>`，不要写站内相对链接。
7. **格式交给 `pnpm format`**。不手排缩进、不手工对齐表格。
8. **篇幅按信息量定，不设配额**：判断标准是 §1.4 的清单写全了没有，不是行数。
